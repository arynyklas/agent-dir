# Triage

Move GitHub issues and external PRs through a small state machine. A PR is an issue with attached code: same roles, same states, plus diff review.

Every tracker comment posted during triage must start with:

```markdown
> *This was generated by AI during triage.*
```

## Reference docs

- [AGENT-BRIEF.md](AGENT-BRIEF.md) — durable agent briefs
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md) — rejected enhancement knowledge base

## Canonical roles

Categories:

- `bug`
- `enhancement`

States:

- `needs-triage`
- `needs-info`
- `ready-for-agent`
- `ready-for-human`
- `wontfix`

Every triaged item should carry exactly one category and one state. The actual repository labels may differ.

## Label discovery and mutation gate

1. Discover existing repository labels before recommending changes.
2. Map canonical roles to exact existing label names.
3. If a label is missing or ambiguous, ask before creating/changing labels.
4. Ask before posting comments, closing items, or changing labels unless the user explicitly requested that exact mutation.
5. Use `github` operations where supported. For tracker mutations unsupported by `github`, use one focused `gh api` call per mutation. Never combine unrelated label, comment, or close changes.

## Reading issues and PRs

- Read issues with `issue://<N>` or `issue://<owner>/<repo>/<N>`.
- Read PRs with `pr://<N>` or `pr://<owner>/<repo>/<N>`; read diffs through `pr://<N>/diff` when needed.
- Use `github` searches for duplicates, related PRs, and prior work.

## Show what needs attention

Present three buckets, oldest first:

1. Unlabeled items.
2. Items mapped to `needs-triage`.
3. Items mapped to `needs-info` with reporter activity since the last triage note.

When external PR triage is in scope, include external PRs in these buckets and tag each line `[PR]` or `[issue]`. Let the maintainer pick.

## Triage a specific issue or PR

1. **Gather context.** Read body, comments, labels, author/date, and prior triage notes. For PRs, read the diff. Search for redundant existing behavior and prior rejected enhancements in `.out-of-scope/`.
2. **Recommend.** Present category, state, label mapping, and reasoning. Wait for maintainer direction before mutating.
3. **Verify the claim.** For bugs, use `systematic-debugging` to reproduce or establish a deterministic evidence path. For PRs, use `receiving-code-review` to evaluate the external diff and feedback path. Report confirmed, failed, or insufficient detail.
4. **Grill if needed.** If the request needs shaping, use `grilling` and `domain-modeling` one question at a time.
5. **Apply the outcome after approval.** Use the mapped labels and the least mutation needed.

## Outcomes

- `ready-for-agent`: post an agent brief using [AGENT-BRIEF.md](AGENT-BRIEF.md).
- `ready-for-human`: post the same structure, but state why it needs a human.
- `needs-info`: post focused triage notes with specific questions.
- `wontfix` because already implemented: point to where it exists; do not write `.out-of-scope/`.
- `wontfix` for rejected enhancement: update `.out-of-scope/`, link it in the comment, then close after approval.
- `needs-triage`: apply the role; optional comment if partial progress matters.

## Needs-info template

```markdown
> *This was generated by AI during triage.*

## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- specific question 1
- specific question 2
```

Questions must be actionable. Do not ask “please provide more info” without naming the missing fact.

## Quick override

If the maintainer says to move an item to a state, confirm the exact label/comment/close changes you are about to make, then apply only those approved mutations. If moving to `ready-for-agent` without a shaping session, ask whether they want an agent brief.

## Resuming

Read prior triage notes first. If the reporter answered a question, update the recommendation instead of re-asking resolved questions.
